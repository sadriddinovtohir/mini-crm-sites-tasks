# Решения и допущения

## Бизнес-правила

1. **Исполнитель назначается сразу при создании задачи** (поле обязательное), и это может быть только пользователь с ролью «Исполнитель». Проверяет триггер `tasks_20_check_assignee` — при создании задачи и при смене исполнителя.
2. **Постановщик может редактировать задачу и менять исполнителя в любом статусе, кроме «Принята».** При смене исполнителя статус не меняется. Прежний исполнитель сразу теряет доступ к задаче (RLS по `assignee_id`), новый видит всю её историю.
3. **Объект нельзя удалить, пока в нём есть задачи** (`on delete restrict`) — защита от случайной потери данных. Сначала нужно удалить задачи.
4. **При удалении задачи удаляется и её история** (`on delete cascade`): история относится только к этой задаче. Отдельно изменить или удалить историю нельзя никому — у клиентов нет ни прав (GRANT), ни политик на запись в `task_status_history`.
5. **Комментарий можно оставить при любой смене статуса;** при возврате на доработку он обязателен (не пустой после удаления пробелов). Максимум 2000 символов.
6. **Имена пользователей видны всем вошедшим** (чтобы показывать автора и историю). Email в `profiles` не хранится, поэтому другим пользователям он не виден.
7. **Роли назначает администратор** в Supabase (`roles.sql` или SQL-запросом). Сменить роль через приложение нельзя. Роль берётся только из `profiles.role`, а не из `user_metadata`, которую пользователь может изменить сам.
8. **Создание задачи записывается в историю** как переход «— → Новая» (триггер `tasks_30_history_on_insert`).
9. **Регистрация отключена**, пользователей создаёт администратор. Новый пользователь всегда получает роль «Исполнитель».

## Технические решения

10. **Три уровня защиты в базе:**
    - **RLS** — какие строки пользователь видит и может менять;
    - **GRANT на колонки** — какие поля вообще можно записать (`status`, `created_by`, даты — нельзя никому из клиентов);
    - **RPC `change_task_status`** — единственный способ сменить статус; таблица переходов и проверка «кто может» — внутри функции.
11. **`select … for update` в RPC** блокирует строку задачи: если два запроса пришли одновременно, второй дождётся первого и увидит уже новый статус (переход не выполнится дважды).
12. **Чужая задача «не находится».** Если исполнитель вызывает RPC для чужой задачи, он получает ту же ошибку «Задача не найдена», что и для несуществующей, — так мы не раскрываем, что задача существует.
13. **Функции-помощники и триггерные функции — в схеме `private`**, которая не открыта через API, с `set search_path = ''`. Права на выполнение у `PUBLIC`/`anon` отозваны; `authenticated` может вызвать только `private.is_manager()` (она нужна политикам RLS).
14. **Проверка исполнителя срабатывает только при создании задачи и при смене исполнителя**, а не при каждом обновлении. Иначе, если исполнителя позже сделают постановщиком, его старые задачи нельзя было бы даже принять.
15. **Пустые названия и адреса запрещены** check-ограничениями (`btrim(...) <> ''`), а не только формой.
16. **Таблица переходов продублирована во фронтенде** (`getAvailableActions` в `src/lib/statuses.ts`) только для того, чтобы показывать нужные кнопки. Источник правды — база.
17. **Тексты ошибок из базы — на русском** (`raise exception … using errcode`). Стандартные ошибки Postgres (нет прав, нельзя удалить объект с задачами) фронтенд переводит по коду ошибки.
18. **«Мои задачи» — экран исполнителя** и его стартовая страница. Постановщик попадает на «Объекты».
19. **`seed.sql` очищает объекты и задачи** перед загрузкой — его можно запускать повторно. Предназначен только для тестовой базы. Автоматический сид в `config.toml` отключён, потому что сиду нужны заранее созданные пользователи.
20. **Скрипт проверки безопасности сам создаёт и удаляет временные данные**, а не опирается на сид. Кроме запретов он проверяет и разрешённые шаги (контрольные пункты) — чтобы ✅ не получались просто потому, что «всё сломано».

## Не сделано (вне рамок задания)

- уведомления;
- фото и вложения;
- поиск и пагинация;
- обновление в реальном времени;
- восстановление пароля.
